# Stock by people: the H3 contract

Status: root contract, 8 October 2026, under the owner's people-first order (rebuild plan §4, H3). Outcome:
**manage business context** — a person keeps the counted stock list from the one client, and counts it in one go.
The owner's finding of 7 October drives this: counting item by item from each thread "is a very annoying way of
counting stock".

## 1. What a person can do when H3 is done

- Open Stocktake from the thread list's Stock filter (a pinned "Stocktake" row while that filter is on) and from a
  stock item's card, see every active item grouped by location with its last count, type the counts they take,
  skip the rest, and save once. Each counted item gets one change line in its thread; the stocktake is one change set
  and one entry in each item's History, undoable item by item under the R3 rules.
- Add an item (name, location, unit, optional reorder point and note) from Stocktake or from a topic ("Make this a
  stock item" is NOT in H3: a stock item has no thread conversation to convert; new items are made on the Stocktake
  screen), edit its details from its card, and archive it with a confirm step. Archived items leave Stocktake and
  the Stock filter; "Show archived" lists them.
- The stock card's fold-out shows location, unit, reorder point, note and the last three counts.

## 2. API

Existing: `GET …/stock?location&includeArchived`, `POST …/stock`, `PATCH …/stock/:itemId` (details, archived,
expectedRevision), `POST …/stock/:itemId/count` (count, note). All journalled (0047).

New: `POST …/stock/stocktake { changeSetId, counts: [{ itemId, expectedRevision, count, note? }] }`, 1–200 items,
one transaction, one change set: every count is written as the per-item count route writes it (same validation,
same observation rows), the stale-revision rule applies per item and refuses the whole stocktake with the stale
item ids (`409 stale_revision { itemIds }`, nothing written), an archived item refuses it (`stock_archived`), the
same `changeSetId` with the same content returns the first result. Response: the counted items as the list returns
them, with the `Change-Set-Id` header. No migration unless the journal needs one (it should not: one change set per
organisation per transaction already holds).

## 3. Client

- **Stocktake** `/stock/stocktake` (design board 12 in docs/proposals/assets/captain-history-undo-2026-10-02/
  Stocktake.dc.html): heading, one-line hint, items grouped by location under spaced-capital labels, each row with
  name, last count with unit, when and by whom, and a numeric field on the right (unit as placeholder; a filled field
  turns the counted style); "Add an item" at the end; a bottom bar with "n of m counted", Cancel and "Save stocktake".
  Save sends the filled rows only, with a client `changeSetId` kept across an uncertain result for an explicit
  "Save again with the same ID"; a stale refusal reloads those rows, marks them and keeps the rest typed; 429 keeps
  the form with its wait. Typed counts survive leaving and returning to the screen in this session (sessionStorage,
  scoped by person and organisation, cleared on save, sign-out or another person), because a stocktake walks the
  building.
- **Add an item** opens a small form in place (name, location with the existing locations offered, unit, reorder
  point, note); one `POST …/stock` with a change set id; the new row appears in its location.
- **Stock card** (the stock thread's unfolded card): details editable as the task card's are, "Archive this item"
  with a confirm step, the last three counts, and a "Stocktake" link.
- **Stock filter**: while it is on, a pinned row "Stocktake · n items" above the groups opens the screen.
- Fidelity: board 12 for Stocktake; the task card (board 1) for the item details; compare with
  `apps/e2e/scripts/mockup-compare.mjs` and record the differences. Both colour schemes; 360/390/430; honest states;
  real inputs with labels; `inputmode="decimal"`.

## 4. Tests

Real Postgres: the stocktake route (one change set, one change line per item, per-item observations, stale item
refusal with nothing written, archived refusal, retry rule, 200-item bound, a non-member refused); undo of one item's
count from a stocktake leaves the others (R3 rules). Client: pure tests for the form, grouping and the persisted
draft; the real-API parser test extended; Playwright at 360/390/430 for a stocktake (type two, skip one, save,
change lines appear), a stale item, an uncertain save then explicit retry, add an item, archive from the card, the
Stock filter's pinned row; dark screenshots. Validation record under `docs/validation/stock-2026-10/`.
