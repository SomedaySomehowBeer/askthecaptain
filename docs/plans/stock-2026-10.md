# Stock by people: the H3 contract

Status: root contract, 8 October 2026, under the owner's people-first order (rebuild plan §4, H3). Outcome:
**manage business context** — a person keeps the counted stock list from the one client, and counts it in one go.
The owner's finding of 7 October drives this: counting item by item from each thread "is a very annoying way of
counting stock".

## 1. What a person can do when H3 is done

- Open Stocktake from the thread list's Stock filter (a pinned "Stocktake" row while that filter is on) and from a
  stock item's card, see every active item grouped by location with its last count, type the counts they take,
  skip the rest, and save once. Each counted item gets one change line in its thread; the stocktake is one change set
  and one entry in each item's History, undoable item by item under the R3 rules.
- Add an item (name, location, unit, optional reorder point and note) from Stocktake or from a topic ("Make this a
  stock item" is NOT in H3: a stock item has no thread conversation to convert; new items are made on the Stocktake
  screen), edit its details from its card, and archive it with a confirm step. Archived items leave Stocktake and
  the Stock filter; "Show archived" lists them.
- The stock card's fold-out shows location, unit, reorder point, note and the last three counts.

## 2. API

Existing: `GET …/stock?location&includeArchived`, `POST …/stock`, `PATCH …/stock/:itemId` (details, archived,
expectedRevision), `POST …/stock/:itemId/count` (count, note). All journalled (0047).

New: `POST …/stock/stocktake { changeSetId, counts: [{ itemId, expectedRevision, count, note? }] }`, 1–200 items,
one transaction, one change set: every count is written as the per-item count route writes it (same validation,
same observation rows), the stale-revision rule applies per item and refuses the whole stocktake with the stale
item ids (`409 stale_revision { itemIds }`, nothing written), an archived item refuses it (`stock_archived`), the
same `changeSetId` with the same content returns the first result. Response: the counted items as the list returns
them, with the `Change-Set-Id` header. No migration unless the journal needs one (it should not: one change set per
organisation per transaction already holds).

As built in S-A (details the contract left open, decided there):

- **Shapes.** `201 { changeSetId, items }`, `items` the counted items as `GET …/stock` returns its rows, in the list's
  order (location, then name). `changeSetId` is required (a stocktake is always retried by the client); item ids are
  unique (`400 stocktake_duplicate`); a count is the count route's (a decimal of zero or more, as a string or a JSON
  number, at most 80 characters) with an optional note of at most 1000 characters; anything else, or 0 or more than 200
  items, is `400 invalid_request`.
- **Order of refusals.** Items are locked in id order after the membership check. Any unknown, foreign or hidden item is
  the generic `404 not_found`. Then every item whose revision moved is named: `409 { code: 'stale_revision', itemIds }`.
  Then, with every revision current, every archived item: `400 { code: 'stock_archived', itemIds }` (400 as the count
  route answers it). Archiving moves an item's revision, so a client that loaded the item before it was archived gets
  `stale_revision`, and its reload shows the item gone. Nothing is written by any refusal, the change set included.
- **The retry rule.** The fingerprint is the counts as parsed (ids lower-cased, counts as decimal strings). A retry with
  the same id, person and counts answers `201` with the counted items as they are now (versions contract §5: "read as it
  is now"); the same id for anything else, or by the count route, is `409 change_set_id_unavailable`.
- **Each count** is the count route's write: one `stock_counts` row with who and the time taken after the row lock, the
  item's current count, when and by whom from it (which moves its revision once), and the `stock.counted` event the
  stocktake workflow listens for. The journal gives each counted item one change line in its thread and one `count`
  entry in its History, all naming the one change set; undoing one item's entry is that item's alone.
- **The card's read**, added for §3's stock card (no route gave the last three counts): `GET …/stock/:itemId` →
  `{ item, counts, locations, timezone }`, `item` a list row (archived or not), `counts` the latest three observations
  `{ id, itemId, count, note, countedAt, countedBy, countedByName }`, newest first, `locations` the active locations.
  `PATCH …/stock/:itemId` now takes an optional `expectedRevision`: when sent, a moved item is `409 stale_revision` and
  nothing is written (the client always sends it; callers that omit it keep today's behaviour).
- **The Stock filter** of `GET …/threads` leaves out archived items' threads (§1); they stay in All and Records.
- No migration: the journal already allows one change set per organisation per transaction touching many records.

## 3. Client

- **Stocktake** `/stock/stocktake` (design board 12 in docs/proposals/assets/captain-history-undo-2026-10-02/
  Stocktake.dc.html): heading, one-line hint, items grouped by location under spaced-capital labels, each row with
  name, last count with unit, when and by whom, and a numeric field on the right (unit as placeholder; a filled field
  turns the counted style); "Add an item" at the end; a bottom bar with "n of m counted", Cancel and "Save stocktake".
  Save sends the filled rows only, with a client `changeSetId` kept across an uncertain result for an explicit
  "Save again with the same ID"; a stale refusal reloads those rows, marks them and keeps the rest typed; 429 keeps
  the form with its wait. Typed counts survive leaving and returning to the screen in this session (sessionStorage,
  scoped by person and organisation, cleared on save, sign-out or another person), because a stocktake walks the
  building.
- **Add an item** opens a small form in place (name, location with the existing locations offered, unit, reorder
  point, note); one `POST …/stock` with a change set id; the new row appears in its location.
- **Stock card** (the stock thread's unfolded card): details editable as the task card's are, "Archive this item"
  with a confirm step, the last three counts, and a "Stocktake" link.
- **Stock filter**: while it is on, a pinned row "Stocktake · n items" above the groups opens the screen.
- Fidelity: board 12 for Stocktake; the task card (board 1) for the item details; compare with
  `apps/e2e/scripts/mockup-compare.mjs` and record the differences. Both colour schemes; 360/390/430; honest states;
  real inputs with labels; `inputmode="decimal"`.

As built in S-B (details the contract left open, decided there):

- **Stocktake.** Rows come in the list's order (location, then name), so board 12's drawn order (Pale, Wheat, Citra) is
  not kept. A count is shown with its digits grouped ("4,200 cans"), and the unit as stored ("1 rolls"; nothing is
  made singular). A row's field is labelled "<name>, <unit>", or just the name when it already holds the unit
  ("330 ml cans"). A bad count is said on its row and turns Save off. "n of m counted" counts the filled rows.
  The back link and a saved stocktake return to the thread list. The list then says "Stocktake saved: n items
  counted. Each count is in its item's thread." once and reloads.
- **Refusals.** A stale refusal marks the named rows ("Changed since you opened Stocktake. Type your count again.")
  and clears their typed counts, because the count someone else just took is what the row now shows. The rest stay
  typed, and the next save takes a new change set id. An archived refusal drops those rows the same way. While a save
  is in flight or uncertain, the form is locked. The uncertain save (its id and body) is kept in session storage with
  the typed counts, so leaving and returning still offers "Save again with the same ID" or Discard. Discard keeps the
  typed counts for the person to check.
- **Cancel** returns to the list. With typed counts it first asks "Discard n typed counts? Nothing has been saved."
  (Keep counting / Discard).
- **Add an item** opens in place under the groups. The existing active locations are offered as choices under the
  Location field. Name, location and unit are required; reorder point and note are optional. "Show archived" sits
  beside it and lists the archived items, each with "Restore" after a confirm step.
- **Stock card.** Name, location (with the same choices), unit, reorder point and notes are saved together with the
  item's revision ("Save changes" / "Discard edits", as the task card). The unit is read-only once the item has
  counts (the API's `stock_unit_counted` rule). Below that come the existing count from the card, then "Last counts"
  (count, when, by whom, note), then the "Stocktake" link and "Archive this item" (or "Restore this item") with a
  confirm step. The card reads `GET …/stock/:itemId` when it unfolds.
- **Stock filter row.** "Stocktake · n items" counts the active items from `GET …/stock`, read when the filter turns
  on. It reads "Stocktake" until that answer arrives.
